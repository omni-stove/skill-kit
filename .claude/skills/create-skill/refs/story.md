# Story create-skill conventions

Conventions the existing story skills establish — follow them when scaffolding a new one:

- **Never hardcode project paths.** Get every path from `.agents/refs/path <project-id> <what>
  [name]` rather than writing a path in the body; the resolver loads that project's own layout file,
  so the skill never learns how paths resolve. If the kind the new skill needs isn't defined, add
  the function name to `.agents/refs/layout-template.sh` and have the user re-run `setup` — don't
  build the path in-model.
- **Push deterministic work into `scripts/*.sh`** under the skill dir, called from the body in one
  line. Resolve refs inside the script so the body stays about the judgment.
- **Extract a shared rule set when it's reused.** If the skill's rule set is shared with other
  skills (detection criteria, output format, fix flow), pull it into `.agents/refs/<topic>-rules.md`
  and load it via a `` Run `.agents/skills/<name>/refs.sh` `` line right after the frontmatter,
  where `refs.sh` cats the rule set; refer to it in the body as "the loaded rules". `chmod +x` the
  refs.sh. `dupcheck` is a working example.
- **For a format-driven skill, reference the format** under `.agents/refs/*-format.md` (cat it in
  the skill's context script) rather than restating a template.
- **Keep each skill self-contained** — never name another skill from the body. Share overlapping
  behavior through the refs mechanism instead of "for X, use the Y skill".
- A per-project slash shortcut (`/<prefix>:<skill>`) is generated by the calling repo's own
  command-scaffolding tool, if it has one — not here.
